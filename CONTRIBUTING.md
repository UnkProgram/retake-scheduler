# Правила работы над проектом

## Ветвление
- Ветка `main` всегда рабочая и защищена: прямые push запрещены.
- Вся работа ведётся в коротких ветках от актуальной `main`.
- Изменения попадают в `main` только через pull request после Approve и успешного CI.

## Именование веток
Формат: `<префикс>/<номер-задачи>-<краткое-описание>` (латиница, нижний регистр, дефисы).

| Префикс | Назначение | Пример |
|---|---|---|
| `feature/` | новая функциональность | `feature/12-csv-import` |
| `bugfix/` | исправление ошибки | `bugfix/27-room-overlap` |
| `docs/` | документация | `docs/31-readme` |
| `test/` | тесты | `test/18-core-tests` |
| `refactor/` | улучшение кода без смены поведения | `refactor/22-split-api` |
| `chore/` | настройка, инфраструктура, CI | `chore/9-ci-setup` |

## Коммиты
Формат: `<тип>(<область>): <описание> (#<номер задачи>)`

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `style`, `chore`, `ci`.

- один коммит — одно логическое изменение;
- описание в повелительном наклонении, до 72 символов;
- номер задачи Redmine указывается всегда;
- не коммитить пароли, токены, личные данные, `.env`.

Пример: `feat(importers): добавить импорт студентов из CSV (#12)`

## Стиль кода
- PEP 8, проверка Ruff, длина строки до 100 символов.
- Имена: `snake_case` для функций и переменных, `PascalCase` для классов, `UPPER_SNAKE_CASE` для констант. Идентификаторы на английском.
- Аннотации типов обязательны для публичных функций.
- Docstring (Google-стиль) для модулей, классов и публичных функций.
- Комментарии на русском, объясняют «почему», а не «что».
- Закомментированный код не оставлять; незавершённое помечать `# TODO(#номер): описание`.
- Новая логика покрывается тестами в `tests/`.

## Code review
1. Взять задачу в Redmine, статус «В работе».
2. Создать ветку от актуальной `main`.
3. Перед PR: обновить ветку от `main`, запустить `ruff check .` и `pytest`.
4. Открыть PR по шаблону, задачу перевести в «На проверке».
5. Назначить ревьюера из таблицы ниже.
6. Ревьюер отвечает в течение 2 дней: Approve или Request changes.
7. Автор исправляет замечания в той же ветке.
8. После Approve и зелёного CI автор делает Squash and merge и удаляет ветку.
9. Задача переходит в «Решена», тимлид закрывает её.

### Чек-лист ревьюера
- изменения соответствуют задаче и не содержат лишнего;
- соблюдены стиль и именование;
- есть тесты, они проходят;
- нет секретов, отладочного вывода, закомментированного кода;
- документация обновлена, если изменилось поведение.
